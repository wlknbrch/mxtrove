# Self-hosting MxTrove

You operate your own instance, accounts, provider applications, database, and
media volumes. The official MxTrove project does not receive your deployment's
credentials or automatically provide storage/support for it. Follow
[TRADEMARKS.md](../TRADEMARKS.md) and [the source-offer requirements](licensing.md).

## UI demonstration

Use Node.js 22 (`nvm use`) and run:

```sh
npm ci
VITE_ENABLE_DEMO_MODE=true npm run dev
```

Open `http://localhost:5173`. Demo mode uses synthetic local data. It does not
prove working OAuth, uploads, protected playback, RLS, or Realtime. Do not use
it as an internet-facing service. Do not add production credentials for a demo.

## Complete local development

Requirements: Node.js 22, npm, Docker Engine/Compose, Supabase CLI, FFmpeg and
ffprobe. Install both dependency sets and create local configuration:

```sh
npm ci
npm --prefix services/media-worker ci
cp .env.example .env
cp services/media-worker/.env.example services/media-worker/.env
supabase start
supabase status
```

Use the **local** Supabase URL and publishable key in `.env`; use the local
server secret/service-role key in the worker's `.env` only. Keep the frontend's
`VITE_MEDIA_WORKER_URL=http://localhost:8080` and
`VITE_APP_URL=http://localhost:5173`. Set a random worker signing secret, e.g.
one generated by `openssl rand -base64 48`.

Set `PROTECTED_MEDIA_DIR=./.data/protected-media` and
`SOCIAL_PREVIEW_CACHE_DIR=./.data/protected-media/social-previews` for the local
worker. These directories hold real attachments/derivatives; preserve them
when testing restart/recovery. The worker runs in `services/media-worker`.

Only against the local database, initialize and test:

```sh
supabase db reset --local
supabase test db
```

The seed creates synthetic accounts with a documented demonstration password;
never apply the seed to an internet-facing/production database.
Start `npm run worker:dev` and `npm run dev` in separate terminals. Configure
at least one cloud OAuth application for real uploads. No provider credentials
are required merely to build the software.

## OAuth and optional features

Create your own applications and allow your own origins/callbacks. See the
[provider setup instructions](../README.md#oauth-providers), replacing official
hostnames with your hostname. Enable the Google Drive API and `drive.file`
scope for Google; use the browser PKCE callback flows for Dropbox/OneDrive.
Public client IDs can be in `VITE_*`; server secrets must never be there.
OAuth providers may impose their own review, quota, and testing restrictions.

Web push is optional. If enabled, generate your own VAPID pair and set
`VITE_WEB_PUSH_PUBLIC_KEY` and `WEB_PUSH_PUBLIC_KEY` to the same public key;
`WEB_PUSH_PRIVATE_KEY` stays in worker configuration. Blank keys disable push.
PWA installation and web push are separate features.

## Production with Docker and Traefik

Use your own Supabase project and a VPS with persistent disk. The supplied
generic Compose recipe expects an existing Traefik reverse proxy, an external
Docker network, HTTPS entrypoint `websecure`, and a certificate resolver.
It does not install Traefik or self-host the Supabase production stack.

1. Point your chosen domain to the VPS and configure Traefik/TLS.
2. Copy `deploy/selfhost.env.example` to `deploy/selfhost.env` and replace all
   placeholders. Use a unique Compose project/router prefix for each instance.
3. Set your operator name/contact, source URLs, Supabase credentials, signing
   secret, and optional provider/push values. The browser receives only
   explicitly named `VITE_*` build arguments, never the whole worker env file.
4. Configure Supabase Auth Site URL and allowed redirects for your HTTPS domain.
5. Link **your** Supabase project, inspect pending migrations, and apply them:

```sh
supabase link --project-ref YOUR_PROJECT_REF
supabase db push --dry-run
supabase db push
```

Do not reset or seed the production database. All application migrations,
including the optimized post-card resolver, are required. Create a backup
before updates. Configure Supabase Auth email delivery for your deployment.

Build and start only your Compose project:

```sh
docker compose --project-name my-mxtrove --parallel 1 --env-file deploy/selfhost.env -f docker-compose.selfhost.yml config --quiet
docker compose --project-name my-mxtrove --parallel 1 --env-file deploy/selfhost.env -f docker-compose.selfhost.yml build
docker compose --project-name my-mxtrove --env-file deploy/selfhost.env -f docker-compose.selfhost.yml up -d --no-build
```

Do not publish `docker compose config` output containing resolved secrets.
Compose publishes no direct web/worker host ports; traffic goes through
Traefik. Protected-media volumes must never be mounted into a static web root.
The old `docker-compose.production.yml` is retained for the official service's
legacy domains; independent installations should use the generic file.

Set `VITE_SOURCE_URL` and `PUBLIC_SOURCE_URL` to your public deployed source
revision. A fork that changes code must offer its own source, not only upstream.
Review and adapt the supplied Terms/Privacy pages to your actual service and
practices. Operator fields are configurable, but changing fields alone cannot
write an accurate privacy policy for every deployment. Replace static branding,
`public/sitemap.xml`, and `public/robots.txt` where appropriate.

## First administrator

Sign up and complete onboarding on your own instance. As database owner in
your Supabase SQL editor, grant the role to the intended existing profile:

```sql
insert into public.app_admin_roles (profile_id, role)
select id, 'admin' from public.profiles where username = 'YOUR_USERNAME'
on conflict (profile_id, role) do nothing;
```

Confirm the profile identity before running it. This is an operator action;
users must never be allowed to grant their own role through editable profiles.

## Verification, storage, and updates

Verify `/worker/healthz`, `/worker/readyz`, and `/worker/source`, plus the app's
Source link. Test signup/login, one cloud connection, an upload/release, protected
playback, public/followers/private visibility, messages, and owner editing.
Confirm unauthorized users cannot read private content. Check mobile too.

Audio/artwork responses should use the cloud-provider/VPS media path rather
than stream through a Supabase Edge Function. The optimized card resolver and
bounded public metadata cache reduce database egress; they do not make usage
zero. Monitor database egress, VPS bandwidth/disk, provider quotas, and costs.

Back up both the database and protected-media volume, and test restoring them
together. Cloud originals stay in their owners' cloud accounts; the derivative
volume is not an originals backup. Never use `down -v` on data you need to keep.

For updates, select a reviewed revision, back up, inspect/apply new additive
migrations, update both source URLs, rebuild frontend and worker, then repeat
the smoke checks. `VITE_*` values are compiled into the frontend and require a
rebuild. The S3 storage class is not a supported production backend yet.
